## Design
- **Engine, setup and comparator:** exactly as run 1 and the 2×2's cell A: the workflow's embedded script at `4382e09`, workflow scaffold, **non-thinking**, Qwen3-8B **Q4_K_M** (the production quantization), local CPU, llama-cpp-python 0.3.36. Only the token cap (3000) and time budget (1800 s) are patched, as in the earlier diagnostics. Comparator: cell A in `reviewer-v1-2x2/results.jsonl` (`4f304caf…11911`), which replicates run 1 exactly.
- **Arm (i), one check per call: 54 calls** = 9 rows × 6 checks. Each call's **task** is one fixed question (below); its **context** is the row's canonical `input` (run 1's byte form, nothing else). The model answers one JSON object: `{"finding": "flag"|"pass", "kind": …, "evidence": …}`. **Code assembles the verdict**: the first flagged check in the fixed order `refs, lost-lines, test-count, diff-stat, self-contradiction, unread-reply` gives the verdict, mapped as refs→`reject:phantom-ref`, lost-lines→`claims-mismatch:lost-lines`, diff-stat→`claims-mismatch:inflated-count`, self-contradiction→`…:self-contradiction`, unread-reply→`…:unread-reply`. For test-count the model supplies `inflated-count` or `stale-count`; a missing or invalid kind defaults to `inflated-count`. No flag → `claims-match`. An unparsable reply counts as not flagged and is reported as malformed. The same six questions are asked on **every** row, controls included.
- **Arm (ii), checks as input: 9 calls.** Task: run 1's job text (`547f9fb1…3025a`). Context: the canonical input plus one block with the six deterministic check results, computed by the merged `reviewerChecks.ts` (PR #357, main `1fc2b55`) by `compute_checks.ts` (`checks.json`, SHA-256 `2b2c4b4a…0ed3`).
- **Payloads:** `payloads.json` (63 items, SHA-256 `d98a4c6c…2cd4`), built by `build_payloads_r3.py` from the frozen git objects, with run 1's manifest (`2416cc9a…3da`) for the job text and the leak-check lists. Each item has its own invocation id and so its own sampling seed. Question hashes (first 16 hex): refs `1946aff7…`, lost-lines `4f0d6c43…`, test-count `0eacafac…`, diff-stat `7fcda92b…`, self-contradiction `cfc7d71e…`, unread-reply `97a1a82c…`.
- **Frozen analysis:** `analyze_r3.py` applies the rules below. It is committed with this file, before any result exists. **Runner:** `run_r3.py`. All hashes are in the commit.
- **Smoke test, disclosed:** two items ran before this freeze, (i) RV-08 refs and (ii) RV-08. Both worked mechanically (prompts verbatim, context check clean). I saw their outputs: (i) flagged the refs, and (ii) answered `reject:phantom-ref`. The real pass re-runs both with the same seeds and the same inputs, so they are not selected or reused.

## Definitions
Blessed traps: RV-02, 03, 05, 07. Controls: RV-01, 06, 09. **T** = traps with a non-`claims-match` verdict (of 6). **K** = exact kind (of 6). **Ctl** = controls `claims-match` (of 3). **Designated check** for each trap: RV-02 lost-lines, RV-03 test-count, RV-04 test-count, RV-05 self-contradiction, RV-07 unread-reply, RV-08 refs. n = 9 with one seed per call, so **a one-row difference is noise by declaration.**

## Reading rules (fixed before the first real run)
- **C-i, decomposition is a lever (arm i only):** at least **2 of the 4 blessed traps are flagged by their own designated check**, with **Ctl ≥ 2 of 3**. A flip caused by a different check than the row's own doesn't count, so random false flags get no credit. A flip with Ctl < 2 is over-rejection, not verification.
- **C-i null:** 0 or 1 such flips. Decomposition doesn't move the blessed traps, so **"the model is the limit" stands for discovery** in this form, with the standing caveats (n = 9, one seed, one model family and precision).
- **Why the settled reading rests on arm (i) alone.** In arm (ii) the answer is in the input. A model that copies it moves the traps without having found anything, so arm (ii) **cannot** test whether the model is the limit.
- **S-ii, seat design (arm ii only):** exact kind on **≥ 5 of 6 traps** and **Ctl = 3 of 3** means the model can emit the exact verdict form from evidence, so a "code detects, model formats" seat is viable on these rows. Otherwise even with the checks given the model can't reliably emit the form, and code must assemble the verdict. **Limit:** the checks were built and canaried on these same rows, so arm (ii) here says nothing about detecting new failures.
- **Surprise clause (registered now):** the expectation is that RV-03 and RV-05 may flip in arm (i), as they did with thinking, and that RV-02 and RV-07 are least likely. If RV-02 or RV-07 flip by their own check, that is surprising and will be reported as surprising.
- **Also reported, not decision rules:** off-target flags (a check flagging a row it isn't designated for, a precision measure), unparsable replies, and per-row verdicts for A, (i) and (ii).
- **Leakage, stated up front:** each arm-(i) question names a failure class. This tests whether the model can *perform* a named check when asked singly. It doesn't test whether it discovers failure classes unprompted.
